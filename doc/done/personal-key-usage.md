## 目标

按请求发生时的付款方持久化累计个人 API Key 消费额度，不受消费日志开关和清理影响。纳入钱包和订阅支付，不计组织付款、无 Key、退款和违规费用；不改变余额或组织账本。

## 验收条件

- 用户列表和搜索从主库读取累计值。新消费和任务补扣独立于日志落库；清理日志和重启不影响累计值。
- 首次升级将仍可明确归属的旧消费日志作为起始值；不会恢复已丢失的历史，不重复导入。
- 验证 SQLite、MySQL、PostgreSQL 的新建与升级，并验证独立日志库（包括 ClickHouse）的历史初始化。

## 实施计划

- 不改现有计费状态机：用量累计不是资金状态变更。主库用户行是累计用量的权威来源，运行时以数据库原子增量更新。启动回补在主库单事务中完成，持久化标记避免重算；失败回滚，重启可重试。副节点等待主库完成初始化。首次上线要暂停旧节点接收计费请求和清理日志，避免旧节点在快照后写入未累计日志。
- 复用现有余额单元格和字段，说明只回补可识别的保留历史。不要把报告用量解释为实际扣款或组织账本。

## 首次上线：停机切换

首次引入 `PersonalKeyUsageBackfillV1` 的版本**不能滚动升级**。先启动副节点会遇到未初始化的主库；仅对调启动顺序也不安全，因为旧节点仍可能结算请求、轮询任务或清理历史日志。以下步骤适用于 `/opt/new-api` 管理的双实例（A 主节点，B 副节点）。普通兼容版本继续用原滚动方式。

1. 安排停机窗口。先把本版本的 `deploy/upgrade.sh` 安装到 `/opt/new-api/bin/upgrade.sh`，备份旧脚本并确认使用的是新脚本。上传后验证发布 SHA-256；用独立的正式版本目录 `vX.Y.Z`，将可执行文件仅安装为 `/opt/new-api/releases/<version>/new-api-billing-maintenance`，不要同时创建 `new-api`。旧脚本找不到标准发布路径，无法滚动安装按此方式暂存的二进制。主库首次回补也会检查维护授权，即使误把新二进制放到旧脚本可见的路径，也不会在没有授权时开始回补。
2. 记录 A、B 原来的启动软链接，确认 systemd 角色、停止配置，以及主库与独立日志库（若有）的备份或恢复点。以 root 运行无状态变更的预检，并用构建时记录的实际 SHA-256 替换示例值。预检不会触发排空、重启或改 nginx；通过后正式执行时会再做一次。

   ```bash
   sudo env EXPECTED_SHA256='<release-sha256>' \
     /opt/new-api/bin/upgrade.sh --billing-preflight vX.Y.Z
   ```

3. 在网关入口启用维护拦截，拒绝新请求（通常返回 503），让已开始的请求收尾。验证所有入口都被拦截，包括代理旁路、任何直连 `3000`/`3001` 的客户端及可继续发出新请求的旧连接；保留脚本所需的本机回环健康探针和 drain socket。暂停并等待其他主机、作业或运维操作停止写入计费/用量数据或清理日志，禁止外部自动化重启旧实例。仅修改 nginx upstream 或触发 drain 不能证明这些条件成立；如果不能隔离，就不要运行正式切换。
4. 确认隔离生效后，以 root 运行下列命令。维护模式不会改 nginx，不接受 `FORCE_RESTART=yes`。脚本先等两个实例的在途 HTTP 请求和 WebSocket 连接归零，再停止两个旧实例。只有两者干净停止后，才给新版 A 提供限本版本的临时回补授权。A 完成回补并通过健康检查后撤销授权，再启动和验证 B。两者都通过后才创建标准发布软链接 `new-api`；之后保留它指向的 `new-api-billing-maintenance` 文件。

   ```bash
   sudo env CONFIRM_BILLING_INGRESS_FENCED=yes EXPECTED_SHA256='<release-sha256>' \
     /opt/new-api/bin/upgrade.sh --billing-maintenance vX.Y.Z
   ```

5. 成功退出后，检查两台实例的 `/api/status`、运行版本和主副节点角色，并只读确认主库 `options` 中 `PersonalKeyUsageBackfillV1=complete`。验证用户列表能读取累计用量，确认主库、已配置的日志库及外部写入方均无异常后，再解除维护拦截。其他暂停的写入方只有升级为兼容版本后才能恢复；旧二进制不得重新加入。

**失败与恢复：** 脚本不会自动撤销维护拦截、恢复旧版本或重试。保持入口拦截，检查脚本日志、两个 unit 的状态、实际运行二进制和主库标记。如果中断发生在停止阶段，先查明旧进程是否全部退出；如果中断发生在新版启动之后，不要根据脚本退出码判断回补未提交。异常终止（如 `SIGKILL`）可能遗留 `/run/new-api-billing-maintenance`；确认没有切换进程在运行并完成现场核查后再移除此文件，禁止把它加入常驻配置。

- **主库标记为 `complete`：** 只向前恢复。核对两个实例的启动链接都指向本次 `new-api-billing-maintenance`，修复故障后先启动 A 并验证，再启动 B 并验证。此时无需维护授权。如果标准发布链接尚不存在，等两个实例都通过验证后，在同一版本目录中补建相对链接 `new-api` → `new-api-billing-maintenance`，再执行第 5 步。不要回滚旧二进制或删除标记，否则新用量可能漏计或被覆盖。
- **主库确认未提交标记：** 只有在所有新版进程均已停止、没有仍可能提交回补的数据库会话时，才可按既有备份和回滚流程恢复 A、B 的旧链接并重新排期。若无法确认这些前提，保持停机并排查，不要强制放流。

## 验证结果

- 设置隔离的 `TEST_MYSQL_DSN`、`TEST_POSTGRES_DSN` 和 `TEST_CLICKHOUSE_LOG_DSN` 后，`go test ./controller -run '^TestUserListPersonalKeyUsage$' -v -count=1` 的 7 个场景全部通过：SQLite 3.50.4、MySQL 8.0.46、PostgreSQL 18.3 的新库与 v1.1.2 等价用户表升级，以及独立 ClickHouse 24.8.14.39 日志库。覆盖重复迁移、回补出错后重试、关闭日志仍累计、清理日志和日志库断开仍能显示原值，以及既有余额和组织用量不变。
- `go build ./...` 通过。前端 `bun run typecheck`、`bun run lint`、`bun run test`（2599 项）、`bun run build` 和受影响文件的格式检查通过。
- 在 `newapi_e2e` 临时 schema 中运行旧网关和升级后的网关。升级后清除全部测试消费日志，列表和搜索仍返回已导入的 2,000,000 额度单位；`/users` 返回新版构建产物。没有改动真实账号或部署生产。
- 全量路由测试的 `TestAccessTokenRouteRulesCoverEveryDashboardRoute` 仍失败：现有面板路由与登记列表不匹配，已在未修改基线复现。
