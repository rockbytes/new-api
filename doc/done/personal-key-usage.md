## 目标

按请求发生时的付款方持久化累计个人 API Key 消费额度，不受消费日志开关和清理影响。纳入钱包和订阅支付，不计组织付款、无 Key、退款和违规费用；统计不改变余额或组织账本。

## 验收条件

- 用户列表和搜索从主库读取累计值。新版节点的消费和任务补扣在结算时累计，不依赖消费日志；清理日志和重启不影响累计值。
- 首次升级只准备兼容新旧版本的增量表结构，不回填历史消费日志。混合版本期间，旧节点结算的用量可能不计入个人 Key 统计，但不能因此漏扣款或跳过结算。
- 在 SQLite、MySQL、PostgreSQL 上验证新建与旧库升级、重复执行结构准备，以及既有数据与旧版读写兼容性。

## 实施计划

- 主库是累计用量的权威来源。新版在资金结算时原子地记录个人 Key 用量，不扫描日志库，不将历史日志导入累计值。
- 首次发布前用新版二进制一次性准备主库结构，再按 B（副节点）→ A（主节点）的普通顺序滚动。UI 展示的是个人 Key 用量统计，不是全历史扣款或组织账本。

## 首次上线：先准备结构，再滚动升级

以下步骤适用于 `/opt/new-api` 管理的双实例。无需停下两台实例或关闭日志清理。此版本有结构变更，不走只允许无结构变更版本的自动发布；先核对实际运行版本与目标版本的差异，确认涉及的变更对旧版兼容。

1. 逐个请求旧节点的 `/api/status`（本机端口 `3000` 和 `3001`），确认两边 `data.enable_batch_update` 均为 `false`。这是进程当前生效的 `BATCH_UPDATE_ENABLED` 状态，不要输出完整服务环境。旧版缓存在内存中、尚未写入主库的钱包扣款无法在 Redis 丢失或不可用时被新版仅凭主库余额判断，因此不要在混合版本期留下这种未落库增量。
   - 任一节点仍启用批量更新时，先保持原二进制版本，将服务配置改为 `BATCH_UPDATE_ENABLED=false`，按 B→A 逐台重启使配置生效。每次先从轮转摘除该实例，排空请求，确认没有后台任务或直连请求继续向该进程写入批次，并在停止前确认待刷批次已写入主库；另一台继续处理和结算流量。旧进程按周期刷写，没有退出时刷写的保证；排空计数归零、等待一个周期或脚本退出成功都不能单独证明待刷扣款已入库。无法确认时中止发布并核对账务，不要强制重启。两台都重新上线后，再检查当前版本及批量更新状态。在旧版仍可能写入同一主库期间，不要重新启用旧节点的批量更新。
2. 将新版二进制安装到标准路径 `/opt/new-api/releases/vX.Y.Z/new-api`，验证构建时记录的 SHA-256。在**与现有 A、B 服务相同的 `SQL_DSN` 环境**中运行一次 `new-api --migrate-billing-schema`，为共享主库新增计费所需的表和列。命令只准备结构，不启动网关，也不读日志回填用量。若两台服务均使用标准的共享 `EnvironmentFile`，可这样运行（替换 `vX.Y.Z`）：

   ```bash
   sudo systemd-run --wait --collect \
     --property=User=newapi --property=Group=newapi \
     --property=EnvironmentFile=/opt/new-api/shared/new-api.env \
     /opt/new-api/releases/vX.Y.Z/new-api --migrate-billing-schema
   ```

   若服务有覆盖配置，以实际生效的 `SQL_DSN` 为准；不要用 `LOG_SQL_DSN`，不要把连接串写进命令行或文档。只有命令成功退出且旧实例仍健康才继续。失败时保留旧实例，检查目标库、权限及数据库锁；修复后可重复运行准备命令，无需回滚已成功添加的结构。
3. 确认 `/opt/new-api/bin/upgrade.sh` 是普通滚动脚本。确认兼容性和结构准备完成后，按正常 B→A 顺序发布。混合版本期间不要手动重置订阅额度：旧版的手动重置不会写入新版用来区分额度周期的 epoch。等 A、B 及其他仍写同一主库的旧节点退出后再恢复此类操作。

   ```bash
   sudo env CONFIRM_BACKWARD_COMPATIBLE=yes EXPECTED_SHA256='<release-sha256>' \
     /opt/new-api/bin/upgrade.sh vX.Y.Z
   ```

   每次摘除一个实例，待排空后重启并验证，再恢复轮转。**不要设置 `FORCE_RESTART=yes`**：它绕过排空失败时的中止保护，可能打断在途请求、WebSocket 或结算，不能保证这些操作完成。排空失败时排查后重试，而不是强行继续。
4. 检查两个实例的 `/api/status`、实际运行版本、主副角色和 nginx 轮转状态。确认新结算会更新个人 Key 用量；未导入的历史和旧节点未记录的统计不代表资金未扣款，不要据此补扣或补填统计。

**发布失败与恢复：** 普通脚本在检测到失败时尝试把健康实例恢复到轮转，但不自动回滚二进制。检查日志、运行版本、健康状态与 nginx 配置后处理，保留已新增的兼容结构；如果仍处于混合版本，继续暂停手动订阅重置。回退也不要删除新增结构或已累计的统计数据。

## 验证结果

- `bash -n deploy/upgrade.sh`、`bash -n deploy/upgrade_test.sh` 和隔离执行的 `bash deploy/upgrade_test.sh` 通过。桩测试覆盖旧维护参数被拒绝、正常 B→A 及 A 排空失败时恢复健康实例轮转；未操作生产服务。
