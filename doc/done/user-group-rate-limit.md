# 用户与分组模型请求限速

## 目标

用全局默认规则限制每个用户的模型请求量，允许为指定用户单独提额或降额；保留现有请求分组的匹配方式，并在命中分组规则时，额外限制该用户在该组的请求量。

本方案确定后端限速语义、首版管理界面和验收条件。不引入组内共享额度、渠道实例或上游容量限制，也不改变模型路由或计费。

## 已确认的规则

2026-11-27 确认：单用户配置覆盖全局默认；用户和分组各自计数，所有适用规则都通过才放行。

### 选用规则与计数范围

| 规则 | 上限来源 | 计数范围 |
| --- | --- | --- |
| 用户级 | 有单用户配置就用单用户配置，否则用全局默认 | 用户 ID；该用户的所有 API Key、所有分组共用 |
| 分组级 | 命中本次请求的分组规则才启用；无匹配规则则跳过 | 用户 ID + 分组；同组的不同用户不共享 |

- 「全局默认」是所有用户共用的一套默认配置，不是所有用户共用的额度，也不是单用户配置的硬上限。单用户配置可以高于或低于默认值。
- 分组沿用现有中间件的取值：优先用 API Key 分组，只有 API Key 未指定分组时才用用户所属分组。API Key 已指定分组但没有匹配规则时，不回头匹配用户分组。限速发生在选渠道之前，不按最终选中的渠道或重试切换到的渠道重新归组。当前取值逻辑见 [`middleware/model-rate-limit.go`](../../middleware/model-rate-limit.go#L121)。
- 总请求数与成功请求数是独立指标，使用同一套全局时间窗口配置。两项都允许设为 `0`，表示该层的该项不限；它不是零次额度，也不能当作缺失配置自动回退到默认值。
- 不把三项配置取最小，也不把用户和分组的配置值取最小后只用一个计数器。对同一指标，在同一时刻由两层各自的剩余额度共同决定能否放行；某层或某项无限制时，不参与这一判断。

### 请求处理

1. 鉴权后进入模型请求限速。总开关关闭时跳过本方案的两层检查。
2. 解析用户级规则，检查用户的总请求数和成功请求数限制；不通过则返回 `429`，归因为用户限速。
3. 查找请求的分组规则。命中则检查该用户在该分组的总请求数和成功请求数限制；不通过则返回 `429`，归因为分组限速。未命中则直接进入下一步。
4. 所有适用检查通过后才放行。在放行时为适用的总请求数计数各记一次；被任一层限速拒绝的请求不应扣减任何一层的额度。两层同时达到上限时，优先归因为用户限速。
5. 请求结束后，按现有成功判定仅为成功请求增加适用的成功计数；失败请求仍计入放行时记录的总请求数，但不增加成功计数。每个入口请求只记录一次，不随渠道重试重复计数。

这里的先后顺序用于说明决策和拒绝归因，不代表先扣用户额度再检查分组。实现需保证并发请求不会因两层分别检查和扣减而重复占用额度；成功计数如需在放行时预留容量，失败或取消后的释放策略在实现前确定。

### 示例

以同一窗口的总请求数为例，假设成功请求数上限未触发，且期间没有额度恢复：全局默认 100 次，用户甲单独配置 200 次，A 组 80 次。

- 用户甲已在 B 组发出 150 次，A 组还未使用。此时 A 组剩 80 次，但用户甲只剩 50 次，所以 A 组还能放行 50 次。
- 如果用户甲先在 A 组用满 80 次，且没有其他请求，A 组会拒绝后续请求；其他未达到分组上限的请求仍可使用用户甲剩余的 120 次。
- 用户甲在 A 组的请求不会占用用户乙在 A 组的额度。

## 首版管理界面

沿用两个现有入口，不新建独立限速管理页。

### 系统设置 → 安全 → 限速

- **模型请求限速**：配置总开关和统计窗口。窗口对两层通用；关闭开关后保留已保存配置，明确提示当前不生效。
- **每用户默认上限**：配置总请求数和成功请求数。说明每个用户独立计数，有单独配置的用户不继承这组值。
- **请求分组额外上限**：复用现有可视化编辑器并保留 JSON 模式。说明优先按 API Key 分组匹配、Key 未指定时才用用户所属分组；上限针对该用户在该组的请求，不在组内共享，也不替代用户上限。移除「分组配置覆盖全局限制」的旧说明。

### 用户管理 → 行操作 → 配置限速

- **继承默认**：只读显示当前默认值。保存后移除已有的单用户配置，以后随全局默认值变化。
- **单独配置**：编辑总请求数和成功请求数。没有已有配置时，首次切换到此模式用当前默认值预填；保存只覆盖用户级规则，分组额外上限依然有效。
- 弹窗注明同一用户的所有 API Key 和分组共用用户级上限。用户列表提供「已单独配置」筛选，不为每个用户重复显示默认值。

### 值与规则来源

- 在可视化界面中，限制值 `0` 显示为「不限」，与「继承默认」「无分组规则」「总开关关闭」区分。输入说明注明 `0` 的含义；JSON 和接口仍使用数字 `0`。用户级「不限」不取消分组限制，分组级「不限」也不取消用户限制。
- 配置项标明来源和统计窗口，分别显示用户级上限和分组额外上限，不合并成一个「生效值」，也不把配置上限当作实时剩余额度。首版不做实时余量、试算器或独立总览页。

## 验收条件

1. 无个人配置时使用全局默认；个人配置可以提高或降低用户上限，删除后回到默认。关闭总开关时跳过两层检查。
2. 同一用户的不同 Key、不同分组以及未匹配分组的请求都计入同一个用户级计数。用户达到上限后，即使换到未用过的分组也不能继续请求。
3. 保留 API Key 分组优先和空分组回退；显式分组无匹配规则时不回退到用户分组。分组计数隔离不同用户及同一用户的不同分组；一个分组用尽不影响该用户仍有额度的其他分组。
4. 总请求数与成功请求数分别触发限速；放行后失败的请求只计总量，限速拒绝不扣减任何一层的额度。两层同时触发时返回用户限速归因。测试覆盖同一用户跨分组并发竞争最后剩余额度的情形。
5. Redis 和内存两种路径均满足上述规则；验证共享 Redis 的多个实例使用同一计数，内存模式继续按实例独立计数。
6. 前后端均接受总请求数和成功请求数为 `0`，保存及重新加载后仍表示该层该项不限，不回退到默认值；另一层的规则仍独立生效。可视化界面显示「不限」，JSON 模式保持数字 `0`。
7. 管理员能保存单独配置、切回继承默认，并用「已单独配置」筛选找到例外用户。总开关关闭后配置保留，界面提示不生效；默认上限和分组额外上限的说明不混淆两层作用。

## 实施计划

1. 开始实现前明确单用户配置存储、两层并发计数、成功计数的并发策略，以及从现有独立分组计数切换时如何处理存量窗口。现有分组规则的含义会从「覆盖默认」变为「额外约束」，上线前核对已有规则的影响。
2. 在模型请求限速中间件中接入规则解析和两层检查，覆盖 Redis 与内存路径，保持现有分组匹配和路由顺序。同步调整分组配置的后端校验、可视化编辑器和 JSON 模式校验，允许成功请求数为 `0`。
3. 更新系统限速设置和用户管理入口，按验收条件补充后端和前端的定向回归测试。

### 实施决定

- 单用户配置独立存储，按用户 ID 查询；没有记录表示继承，显式的零值仍是独立配置。
- Redis 和内存用相同的滑动窗口语义。总请求在准入时记录，成功上限在准入时预留，成功完成后转为按完成时间计数，失败、取消或 panic 只释放预留。用户和分组一起检查及记账。Redis 使用新键空间，旧计数不并入；滚动部署的混合版本期间两套计数独立，建议在低流量时切换。
- Redis 预留有时效，长请求定时续约，进程异常退出后由过期回收。Redis 不可用时不降级到本机计数；意外中断导致预留过期的极端情况下，不允许迟到的完成事件恢复旧预留。
