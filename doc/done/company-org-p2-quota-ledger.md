# 公司组织 P2：额度账本

本计划是 [公司组织、成员权限、额度计费、用量看板与账单导出方案](../todo/in-progress/company-organization-membership-quota-billing-usage-dashboard-export.md) 的子计划之一。产品决策以总方案的「已确定的设计决策」为准。本计划的额度模型已按 2026-10-27 的确认意见调整（见「设计要点」），总方案的 D1、D2、D4、D10 需要同步修订。

**依赖**：P1（组织与成员关系）。

## 目标

1. 组织有一个总额度（平台发放累计），组织已用额度为所有成员用量之和，组织剩余 = 总额度 − 已用额度。
2. 每个成员有一个分配量（上限），由 Root 或组织管理员设置，并记录其用量。成员剩余 = 分配量 − 用量。
3. 请求同时受成员剩余和组织剩余约束。两者分别使用不同的错误码。
4. 账本记录所有额度变动：平台发放、预扣、结算差额、退款、结算超出（shortfall）。每条记录关联操作者、目标成员、金额、请求 ID。

## 验收条件

- 组织已用额度始终等于所有成员用量之和，且不超过组织总额度（可通过查询验证）。
- 分配量只是上限，允许超过组织剩余（超分配）。分配不转移额度。
- 预扣同时检查成员剩余和组织剩余，任一不足即拒绝，并分别返回 `insufficient_member_quota` 或 `insufficient_organization_quota`，两者都不扣减。
- 结算差额最多扣到两者剩余中较小的一个，超出部分记为 `shortfall`，不扣款。
- 分配量不能低于该成员已有的用量。
- 停用成员只禁止使用，分配量、用量、组织额度保持不变。
- 人工退款仅 Root 可发起，退款金额不超过该请求的已结算金额，并且幂等。退款退回该成员的用量。
- 组织管理员只能设置组织普通成员的分配量，不能设置自己和其他组织管理员的分配量。Root 可以设置所有人的分配量。
- 重复预扣、重复结算、重复退款不会重复计入（幂等键由请求 ID、序号和事件类型组成）。
- 个人钱包的充值、兑换码、签到奖励、`UserQuotaAdjustment` 人工调额行为保持不变。

## 设计要点

- **额度模型（已确认，模型 B）**：
  - 组织：总额度 G 由平台发放累计，只能通过账本的发放记录增加。已用 U 等于所有成员用量之和。剩余 = G − U。
  - 成员：分配量 A 是上限，由 Root 或组织管理员设置，不从任何地方扣减。用量 u。剩余 = A − u。
  - 准入：预扣额必须同时满足 成员剩余 ≥ 预扣额 且 组织剩余 ≥ 预扣额。成员检查先于组织检查。
  - 结算：正差额封顶到两者剩余较小者，超出记为 `shortfall`；负差额退款。
  - 停用成员：只禁止预扣，不改变任何余额或用量。
  - 删除成员：分配量随账号删除，已发生的用量仍计入组织已用额度，不需要回收。
  - 不再有"未分配池""员工划拨桶"和"分配回收"的概念。
- **错误码**：`insufficient_organization_quota`（组织剩余不足）和 `insufficient_member_quota`（成员分配用完），两者都需要同步到前端错误映射和 7 种语言文案。
- **分配权限**：Root 可设置任何成员的分配量。组织管理员只能设置组织普通成员（角色为 member）的分配量，不能设置自己和其他组织管理员的分配量。
- **账本字段**：账本需要 `request_id` 字段，用于人工退款的已结算金额校验。
- **事件类型**：`grant`、`preconsume`、`settle`、`refund`、`shortfall`。
- **扩展性**：事件类型使用可扩展的枚举。
- **与现有模型的关系**：`model/user_quota_adjustment.go` 只服务个人账户，本计划不修改其行为。

## 实施计划

1. 定义 `OrganizationQuotaAccount`（总额度与已用额度）、`OrganizationMemberQuota`（分配量与用量）和账本表，补充唯一约束（幂等键）和索引。编写迁移。
2. 实现账本服务：平台发放、设置分配量、预扣、结算、退款、人工退款。所有写操作在事务内完成并使用 `lockForUpdate(tx)`。
3. 实现组织额度 `FundingSource`：预扣、结算、退款，接入 `BillingSession` 的资金来源选择，并映射两个错误码。
4. 实现管理接口：Root 发放额度、Root 与组织管理员设置分配量（按上述权限）、Root 人工退款、对账查询。
5. 实现对账查询，用于验证守恒关系，并提供给 P4 的汇总卡片使用。
6. 前端：组织额度管理页面（Root 与组织管理员按权限操作），错误码映射与 7 种语言文案。
7. 编写并发、幂等、超分配、退款边界的测试，使用项目共享的测试约定。
8. 在三种数据库上执行验证。

## 验证结果

截至 2026-10-27，已完成的验证：

- **测试**：额度模型测试（分配量作为上限、预扣双重检查、两个错误码、结算封顶与 shortfall、分配下限、人工退款上限与幂等、停用成员保留分配与用量、并发预扣不超发）在 SQLite、MySQL 8.0、MySQL 5.7、PostgreSQL 17、PostgreSQL 9.6 上全部通过。
- **并发**：并发预扣在 MySQL 与 PostgreSQL 上（真实行锁）不超发，结果与 SQLite 一致。
- **接口**：组织控制器测试（含分配权限：组织管理员可设普通成员的分配量，不能设自己和其他管理员；Root 可设任何人）在 SQLite、PostgreSQL 17、MySQL 8.0 上通过。
- **服务层**：资金来源测试（成员限额拒绝且不回退、组织限额拒绝、结算封顶、退款只生效一次）在 SQLite 上通过。
- **门禁**：`model`、`service`、`relay/common`、`controller`（组织相关测试）的 Go 测试通过；`relaykit` 独立构建通过。
