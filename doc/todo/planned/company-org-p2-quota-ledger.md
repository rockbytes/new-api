# 公司组织 P2：额度账本

本计划是 [公司组织、成员权限、额度计费、用量看板与账单导出方案](./company-organization-membership-quota-billing-usage-dashboard-export.md) 的子计划之一。产品决策以总方案的「已确定的设计决策」（D1–D10）为准。

**依赖**：P1（组织与成员关系）。

## 目标

1. 实现公司未分配池与员工划拨桶（member allocation）两类余额，员工划拨桶独立于个人钱包 `User.Quota`（D1）。
2. 实现账本事件：平台发放（D8）、划拨、回收、预扣、结算差额、退款、人工调整，每条记录关联操作者、目标账户、金额、请求或任务 ID。
3. 将划拨桶接入 `FundingSource` 抽象，供 P3 的付款组织 Key 使用（D2、D3）。
4. 实现成员离开时的自动回收（D4）和已结算消费的人工退款规则（D10）。
5. 划拨额度不过期（D9），余额守恒可以通过查询对账。

## 验收条件

- 总发放额度 = 公司已用额度 + 公司未分配余额 + 员工划拨余额之和，任何时刻可以通过查询验证。
- 划拨只转移未分配池余额，不改变公司可用总额；消费减少员工划拨余额并增加公司已用额度。
- 回收只能回收员工尚未消费的划拨余额，已消费部分不能通过回收冲销。
- 员工离开或被移除时，未消费划拨在同一事务内回收至公司未分配池并记账（D4）。
- 人工退款退回原员工划拨桶并关联原请求；员工已离开时退回公司未分配池；退款金额不超过该请求的已结算金额（D10）。
- 平台发放只能由 Root 操作，并记录原因；不允许无来源写入额度（D8）。
- 并发划拨与并发预扣不能超发或透支，余额不为负。
- 重复回调、重复结算、重复退款不会重复扣减或退款（幂等键由请求 ID 或任务 ID 加事件类型组成）。
- 个人钱包的充值、兑换码、签到奖励、`UserQuotaAdjustment` 人工调额行为保持不变。

## 设计要点

- **资金来源**：在 `service/funding_source.go` 的 `FundingSource` 接口下新增划拨桶实现，与 `WalletFunding` 并列。`BillingSession` 根据 Key 的付款归属选择资金来源，不做回退（D3）。
- **并发与缓存**：`model/user.go` 中 `IncreaseUserQuota` / `DecreaseUserQuota` 在 `BatchUpdateEnabled` 时把写库放入批量队列，缓存更新通过 `gopool.Go` 异步完成；`model/quota_reserve.go` 也有类似分支。划拨、回收、预扣、结算必须同步、同事务写库，不走批量分支。数据库为权威来源，Redis 缓存如需使用，只能作为读取加速，并定义失效方式。实施前需确认是否复用 `TryReserveUserQuota` 的缓存逻辑，推荐新建划拨桶的原子预扣函数，不复用个人钱包的缓存路径。
- **行锁**：需要 `SELECT ... FOR UPDATE` 的查询使用 `lockForUpdate(tx)`（`model/locking.go`），不使用旧式 `tx.Set("gorm:query_option", ...)`。
- **计费规则**：本计划触及预扣、结算、退款，实施前必须完整阅读 `.agents/rules/billing.md`，并遵守其中的溢出、饱和和日志审计要求。
- **扩展性**：账本事件类型使用可扩展的枚举，划拨桶的过期字段和预算重置规则不在 v1 实现，但不得破坏现有事件模型。
- **与现有模型的关系**：`model/user_quota_adjustment.go` 只服务个人账户，本计划不修改其行为。

## 实施计划

1. 定义 `OrganizationQuotaLedger` 与划拨桶余额表，补充唯一约束（幂等键）和必要索引，编写迁移。
2. 实现账本服务：平台发放、划拨、回收、成员离开回收、人工退款、人工调整，所有写操作在事务内完成并使用 `lockForUpdate(tx)`。
3. 实现划拨桶 `FundingSource`：预扣、结算差额、退款，接入 `BillingSession` 的资金来源选择。
4. 实现对账查询，用于验证守恒关系，并提供给 P4 的汇总卡片使用。
5. 编写并发、幂等、守恒和退款边界的测试，使用项目共享的测试约定。
6. 在三种数据库上执行验证。
