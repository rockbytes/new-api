# 公司组织 P1：组织租户与授权

本计划是 [公司组织、成员权限、额度计费、用量看板与账单导出方案](./company-organization-membership-quota-billing-usage-dashboard-export.md) 的子计划之一。产品决策以总方案的「已确定的设计决策」为准。

## 目标

1. 建立组织（Organization）与成员关系（OrganizationMembership）两个租户实体，支持 `pending_admin`、`active`、`suspended` 等状态。
2. 实现平台 Root 创建组织、指定或邀请首位公司管理员的流程，首位管理员激活后组织才进入 `active`。
3. 实现公司角色 `admin` 与 `member` 的服务端授权，组织范围只能来自已验证的成员关系，不信任客户端传入的组织 ID。
4. 保证组织始终至少有一位有效管理员；移除或降级最后一位管理员的操作被拒绝。
5. 不改变 `User.Role` 的平台角色语义，公司管理员不会被映射为平台 Admin。

## 验收条件

- Root 可以创建、停用、恢复组织，设置初始管理员；普通用户和公司管理员不能执行这些操作。
- 邀请接受前组织保持待激活状态；邀请失败重试是幂等的，并留有审计记录。
- 移除、降级、停用最后一位有效管理员的请求均被拒绝，除非同一事务中先任命了替代管理员。
- 公司管理员只能列出和管理本公司成员；改写路径参数、请求体、查询参数访问其他公司资源时返回拒绝。
- 员工只能看到自己的成员关系，看不到「组织管理」入口对应的接口数据。
- 成员关系对 `user_id` 建立唯一约束（v1 一人一公司）；约束只放在成员关系表上，便于以后放开。
- 组织状态流转由显式的状态转换表约束，非法转换被拒绝（可参考 `state-machine` 技能）。

## 设计要点

- **授权模型**：现有 `service/authz/` 基于 Casbin 和用户级覆盖策略（`SetUserPermissions`），面向平台级权限。组织范围权限不建议直接写成 Casbin 策略，因为 `service/authz/authz_test.go` 中已有「旧版带 scope 的策略不扩展权限」的约定。推荐方案：组织角色到操作的映射在服务层以目录形式定义（`organization.*` 操作名与总方案一致），每次请求通过成员关系实时解析，不引入新的 Casbin 维度。实施前需复核该推荐。
- **邀请与认证**：邀请涉及账号创建和密码设置，属于 AGENTS.md 要求的认证流程。实施前必须列出适用的 OWASP ASVS 版本与条目，至少覆盖：
  - 邀请 token 随机生成、只存哈希、单次使用、有过期时间；
  - 对已存在邮箱的邀请返回与新邮箱一致的响应，防止账号枚举；
  - 接受邀请后轮换会话；
  - 审计事件不记录 token、密码或会话凭据。
- **扩展性**：组织与成员关系字段保持最小化，不把「一人一公司」编码进表结构之外的地方，便于以后支持多公司成员。
- **数据库**：新表、唯一约束和索引必须在 SQLite、MySQL、PostgreSQL 上通过，并使用 `lockForUpdate(tx)` 处理并发的管理员变更。

## 实施计划

1. 定义 `Organization`、`OrganizationMembership` 模型、状态枚举与状态转换表，并编写 `AutoMigrate` 与迁移测试。
2. 实现组织服务层：创建、停用、恢复、指定管理员、邀请、接受邀请、成员增删改、角色变更。所有写操作使用事务和 `lockForUpdate(tx)`。
3. 实现组织权限目录与服务端校验函数，供后续 P2–P5 复用。
4. 实现管理接口：平台侧（Root）与公司侧（组织管理）分别路由，公司侧接口从成员关系解析组织范围。
5. 实现邀请流程与审计事件，接入 OWASP 控制项。
6. 编写授权矩阵测试（Root、公司管理员、公司成员、无公司用户、跨公司访问）及最后管理员保护测试。
7. 在三种数据库上执行迁移验证（见下）。
