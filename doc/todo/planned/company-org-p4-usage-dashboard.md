# 公司组织 P4：用量看板重构

本计划是 [公司组织、成员权限、额度计费、用量看板与账单导出方案](./company-organization-membership-quota-billing-usage-dashboard-export.md) 的子计划之一。产品决策以总方案的「已确定的设计决策」为准。

**依赖**：P3（付款组织快照），以及 P1 的组织权限目录。

## 目标

1. 用一个统一的「数据范围解析」服务决定每个请求的数据范围，看板、日志、导出（P5）共用同一套授权和过滤实现。
2. 按角色提供三种视图：平台管理员（全部组织汇总、单个组织、组织内单个用户）、公司管理员（当前组织汇总与成员）、普通成员（本人）。
3. 下线普通用户和公司管理员可见的旧模型分析、流量、用户统计入口；平台运维健康与通道指标保留在独立的平台管理区域。
4. 页面标题下显示统计范围、筛选时间、时区、数据更新时间和消费口径。

## 验收条件

- 平台管理员查看用户时必须先选择组织，不能仅凭用户名定位，未归属组织的用户单独标识。
- 公司管理员的组织范围来自已验证的成员关系，直接修改组织 ID、用户 ID、路径或筛选参数不能扩大范围。
- 普通成员没有成员筛选器，只能看到本人数据；本人发起但由公司承担的请求在个人视图中标注付款归属。
- 汇总卡片、图表、明细、排行使用同一范围和口径；不同计量单位不合并，额度标记为平台额度单位，不显示为真实货币。
- 默认统计最终结算消费；预扣不计入消费，失败且未收费的请求不计入消费，退款和调整计入净消费并可追溯。
- 成员离开组织后，组织历史报表仍按消费时的快照显示历史用量。
- 旧接口（`/api/data`、`/api/data/self`、`/api/data/users` 等）在新接口迁移完成后停用，或收紧为明确的平台管理用途，不能被旧页面绕过新的范围授权。
- 公司管理员可见的日志字段有明确白名单：不包含提示词、请求和响应正文，以及上游渠道、IP、上游错误等运维字段，除非有对应的平台权限。

## 设计要点

- **数据源**：当前 `model/usedata.go` 把看板数据按小时写入 `quota_data`，没有组织维度，不能作为公司边界。新看板基于 P3 的快照字段查询 `Log`（或新增的按小时聚合表）。推荐的数据源需要在实施前做查询计划和数据量评估；如果直接查询明细表的性能不足，再新增带组织维度的聚合表，并同样支持三种数据库。
- **可见字段**：`model/log.go` 中的 `Log` 包含 `ChannelId`、`Ip`、`Other` 等字段。公司侧接口使用字段白名单，`admin_info` 继续只对管理员可见。
- **前端**：`web/src/features/dashboard/api.ts` 当前按角色选择 `/api/data` 或 `/api/data/self`。新页面需遵守 `web/AGENTS.md`：先搜索并复用 `web/src/components/` 中的共享组件，新增通用 UI 需要说明为何不能复用。数字与额度展示复用 `@/lib/format` 与 `@/lib/currency`，传给 `Intl.*` 的语言必须经过 `toIntlLocale`。
- **国际化**：所有新增文案按 `web/src/i18n/locales/` 中的 7 种语言同步，使用 `i18n-translate` 技能。
- **时间**：查询以 Unix 时间戳为准，页面显示实例配置的时区和精确起止时间。
- **扩展性**：数据范围解析服务输入为「调用者身份 + 请求意图」，输出为「可查询的范围条件」。以后新增范围（如多公司、全平台未归属）只需扩展解析器。

## 实施计划

1. 实现数据范围解析服务，覆盖平台、公司管理员、普通成员和未归属用户，并编写表驱动授权测试。
2. 实现新看板的后端查询接口：汇总、趋势、模型分布、排行、明细（分页），所有接口复用同一解析服务。
3. 实现公司侧字段白名单与平台侧字段权限。
4. 实现前端新看板页面，按角色展示范围和筛选条件，复用项目现有组件。
5. 迁移旧入口：下线普通用户和公司管理员的旧模型分析、流量、用户统计入口；平台运维指标迁入独立的平台管理区域。
6. 停用或收紧旧接口，并确认没有前端页面仍在调用。
