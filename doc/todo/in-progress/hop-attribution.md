# 链路归属定位

## 目标

排查用户调用报错时，管理员能从错误日志直接判断问题出在哪一段连接：

- **用户侧**：用户与我们源站之间的连接（第一段）。
- **源站到上游**：我们源站与上游（中转站或厂商）之间的连接（第二段）。
- **源站自身**：不属于两段连接的内部错误。

判定只需要说明是哪一段，不需要定位到段内的具体节点。

## 非目标

- 不向上游传递任何 ID，也不新增发往上游的请求头。
- 不区分中转站与其后面的厂商。上游链路的失败只标记为「源站到上游」，并附带上游主机信息，由管理员自行判断。
- 不改表结构，不做数据库迁移。
- 不解决流式「上游正常关闭但没有完成信号」的归因问题，这需要单独确定各协议的完成条件。

## 设计

### 1. 链路时间线

每个请求在上下文中保存一份时间线（`HopTrace`），相对于请求开始时间记录毫秒数。只记录发生过的事件，未发生的字段为空。

第一段（用户侧）：

| 字段 | 含义 |
| --- | --- |
| `client_disconnect_ms` | 收到用户断开或取消的时间 |
| `client_write_error_ms` | 向用户写数据失败的时间 |
| `client_bytes` | 已向用户发送的字节数 |

第二段（源站到上游）：

| 字段 | 含义 |
| --- | --- |
| `upstream_headers_ms` | 收到上游响应头的时间 |
| `upstream_first_chunk_ms` | 收到上游首个数据块的时间 |
| `upstream_done_ms` | 上游结束（正常完成或关闭）的时间 |
| `upstream_error_ms` | 上游连接出错的时间 |
| `upstream_error_kind` | 出错类型：`connect`（连接失败）、`header_timeout`（响应头超时）、`idle_timeout`（流式空闲超时）、`reset`（连接被重置或读取错误）、`eof_incomplete`（关闭但没有完成信号，预留） |
| `upstream_status` | 上游返回的 HTTP 状态码 |
| `upstream_bytes` | 从上游收到的字节数 |
| `upstream_host` | 上游主机名（不含路径和密钥） |

### 2. 判定规则

`fault_side` 的取值与判定顺序：

1. **源站自身**：错误不来自上游，也不来自用户连接（例如路由失败、额度不足、参数错误、内部 panic）。
2. **用户侧**：用户断开，或向用户写数据失败，并且这一事件早于上游的错误或结束。
3. **源站到上游**：上游连接出错（`connect`、`header_timeout`、`idle_timeout`、`reset`），并且这一事件早于用户侧的断开。
4. **上游服务返回错误**：上游正常响应，但返回了 4xx 或 5xx。归属到「上游」，但不属于链路故障。
5. **无法判定**：以上都不满足。

判定原则：**先发生的事件决定归属**。用户断开后源站取消上游请求，上游的取消错误属于结果，不作为原因。

`fault_reason` 记录判定依据，例如「用户在收到首个数据前断开」「上游在 1200 毫秒后重置连接」。

### 3. 写入位置

- 时间线、判定结论都写入 `admin_info`，只有管理员和 root 可见。
- 错误日志和消费日志都使用同一套判定结果。

### 4. 日志详情展示

管理员的日志详情里增加「链路」区块：用一条时间线同时展示用户侧和上游侧的事件，并显示 `fault_side` 和 `fault_reason`。

## 验收条件

- 每个判定规则都有单元测试，覆盖先发生的事件决定归属的情况。
- 故障注入覆盖以下场景，并且判定结论正确：
  - 用户流式中途断开（预期：用户侧）
  - 上游连接被拒绝（预期：源站到上游）
  - 上游响应头超时（预期：源站到上游）
  - 上游流式中途重置（预期：源站到上游）
  - 上游流式空闲超时（预期：源站到上游）
  - 上游返回 500（预期：上游服务返回错误）
  - 模型不存在（预期：源站自身）
- 普通用户的日志中看不到链路信息。
- 对外响应的内容不变。
- 不改表结构，不增加向上游发送的内容。

## 实施计划

1. 定义 `HopTrace` 和判定函数，补充表驱动单元测试。
2. 在上游请求的位置记录响应头、状态码和上游主机。
3. 在流式扫描器的位置记录首个数据块、结束、超时、重置和用户断开。
4. 在向用户写数据的位置记录写入失败和已发送字节数。
5. 在写入错误日志和消费日志时附带判定结论。
6. 在管理员日志详情中展示链路区块，并补充前端测试。
7. 重新做故障注入验证，记录结果。

## 实施取舍

- 首个数据块时间和字节数本次未实施。判定只依赖链路上的失败事件和结束事件，这两项不影响判定结论，后续需要时再补。
- 链路时间线按请求的每次尝试记录（重试时重新开始）。task 类请求（异步任务、插件）未接入，本次只覆盖对话和普通中继请求。
- 流式结束时间取 select 返回的时刻，精度约为毫秒级。
- 「上游正常关闭但没有完成信号」仍记为正常结束，没有判定，与链路归因的边界一致，留待完成条件确认后处理。

## 验证结果

- 单元测试：`relay/common` 中的判定表测试覆盖「先发生的事件决定归属」、上游错误分类、流式结束映射，以及空链路的安全性，全部通过。
- 服务层和控制器测试：`service` 通过；`controller` 中与中继、错误日志相关的测试通过。`TestResponsesStreamOutcomesPreserveAccounting` 在上一个提交上也失败，与本次改动无关。
- 前端：`usage-logs` 相关测试 446 个用例通过，lint、格式、类型检查通过。
- 故障注入（本机独立的 SQLite 库，上游为本地模拟服务，不使用共享数据库）：

  | 场景 | 客户端结果 | fault_side | fault_reason | 结论 |
  | --- | --- | --- | --- | --- |
  | 上游返回 500 | 500 | upstream_service | upstream_http_status | 正确 |
  | 上游返回 400 | 400 | upstream_service | upstream_http_status | 正确 |
  | 上游不返回响应头（超时） | 500 | upstream_link | upstream_header_timeout | 正确 |
  | 上游连接被拒绝 | 500 | upstream_link | upstream_connect | 正确 |
  | 上游流式中途重置 | 200（已开始输出） | upstream_link | upstream_reset | 正确 |
  | 上游流式空闲超时 | 200（已开始输出） | upstream_link | upstream_idle_timeout | 正确 |
  | 用户流式中途断开 | 无 | client_link | client_disconnected | 正确 |
  | 模型不存在 | 503 | gateway | gateway_internal | 正确 |
  | 额度不足 | 403 | gateway | gateway_internal | 正确 |
  | 请求参数错误 | 400 | client_request | invalid_request | 正确 |
  | 上游正常关闭但没有完成信号 | 200 | 无 | 无 | 未判定，见实施取舍 |

- 验证结束后已停止本地网关和上游模拟服务。
- 数据库：本次没有改表结构，字段写入已有的扩展信息，不需要三库验证。
