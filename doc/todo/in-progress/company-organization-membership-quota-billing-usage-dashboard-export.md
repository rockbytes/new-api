# 公司组织、成员权限、额度计费、用量看板与账单导出方案

## 背景

当前平台以独立用户账户为主要额度主体。用户的余额和累计消耗记录在用户账户上；`User.Role` 表示平台级角色，`User.Group` 用于模型可用范围和计费倍率。分组不是公司边界，平台管理员也没有仅限于一家公司的成员管理与用量查看权限。

模型定价侧已经有表达式计费和任务插件用量事实机制。表达式负责计算应扣额度，任务插件可以声明秒数、数量、Token、积分及枚举、布尔类计费事实；预扣、结算和退款仍由 New API 主机负责。本方案保留这条计费链路，为公司/员工额度增加独立的账户归属与额度划拨能力，并明确覆盖不同视频服务的差异化计量：Ark/Seedance 可按实际 Token 或任务字段结算，其他 Seedance 接入可能按秒计价，Sora、Wan 和 Kling 分别使用秒数/规格或供应商资源单位。

## 目标

1. 平台 Root 能创建公司组织、设置公司总额度、指定首位公司管理员，并暂停或恢复组织服务；不创建代表公司的特殊用户账号。
2. 公司管理员能在本公司范围内创建员工账号、停用或删除员工、重置员工密码，并分配和收回未消费额度。
3. 员工使用自己账号拥有的 API Key 调用模型；Key 可指定由公司承担费用，消费仍归属到实际用户并同时记入付款公司。
4. 公司管理员能查看本公司的总额度、未分配额度、已分配余额、累计消耗，以及按员工、模型和时间筛选的调用记录。
5. 计费规则继续使用 New API 的模型定价表达式和任务插件用量事实。GPT、Claude、GLM、DeepSeek 等按 Token/缓存/上下文档位计费；Doubao、Seedance 等任务类模型按插件报告的秒数、数量、分辨率、音频选项或供应商额度计费。
6. 平台管理员保留跨公司管理能力；公司管理员和员工不能访问其他公司的账户、密钥、余额、消费日志或任务记录。

## 范围与业务约定

### 额度语义

本方案将“公司给员工分配额度”定义为**余额划拨**，而不只是设置一个消费上限：

- 平台向公司发放或调整额度后，额度进入公司的未分配余额。
- 公司管理员将额度划给员工时，公司未分配余额减少，员工可用余额等额增加；公司总可用额度不因此减少。
- 员工消费时，员工可用余额减少，公司已用额度增加。
- 公司管理员收回额度时，只能收回员工尚未消费的余额；已消费部分不得通过额度回收冲销。
- 公司可用额度满足：`未分配余额 + 公司员工可用余额之和`。公司已用额度单独累计。发放、划拨、消费、结算差额、退款、回收和人工调整都必须留有账本记录。
- 在不考虑过期/人工核销时，公司总发放额度满足：`总发放额度 = 公司已用额度 + 未分配余额 + 公司员工可用余额之和`。

这种定义符合当前 New API 以配额余额扣减的业务模式，并能防止同一份额度既留在公司又分给员工。若产品最终只要求“公司总消费上限 + 每人个人消费上限”，应将其作为不同的预算模式设计，不与余额划拨混用。

### 身份与权限

- v1 中一个员工账户只加入一个公司。多公司成员身份留待后续设计，避免一个个人余额同时归属多个公司。
- v1 的员工额度是持续余额，没有自动月度重置；公司管理员可以追加划拨或收回未消费部分。若需要月度预算重置，作为后续独立预算模式设计。
- `User.Role` 继续只表示 Root、平台 Admin、普通用户等平台角色。公司成员关系单独保存公司角色，v1 至少区分 `admin` 和 `member`；公司管理员不因此成为平台 Admin。
- `User.Group` 继续表示模型可用分组及相关计费倍率；不得把它作为公司租户 ID 或公司管理员权限来源。
- 公司管理员是公司范围的角色，不能通过普通用户创建/更新接口授予平台 Admin/Root 权限。
- 客户端传入的组织 ID 不能作为授权依据。服务端必须从已验证的用户成员关系或 Key 固定的付款组织解析范围，并校验该用户有权使用该组织付款。

### 创建公司组织与首位管理员

平台管理员在「公司组织」管理入口创建组织。组织是独立的租户实体，不需要先创建一个代表公司的特殊用户账号。创建流程要求同时设置首位公司管理员，由 Root 直接创建账号（见 D11）：

1. 平台管理员填写公司组织资料，并设置首位公司管理员的用户名和初始密码，创建组织。组织创建即为 `active`。
2. 服务端创建普通用户账号（不授予平台角色），账号首次登录必须修改密码（见 D12）。
3. 服务端在同一事务内创建该账号与组织的成员关系，成员关系为 `active`，并明确授予公司 `admin` 角色。
4. 创建失败时不留下部分数据；操作写入审计日志，日志不记录密码。
5. 组织至少保留一位有效公司管理员。停用、移除或降级最后一位管理员前，必须先完成另一位管理员的任命。

平台菜单在管理区增加「公司组织」，供 Root 创建和维护组织。公司管理员登录后在常规菜单看到「组织管理」，至少包含成员管理、预算与用量、组织设置。组织管理菜单只面向公司管理员显示；接口仍需逐项执行服务端组织角色校验。普通成员不显示该管理菜单，但可通过常规「数据看板」查看本人用量。

### 用户账号与 API Key 归属

- API Key 始终属于一个具体用户账号。现有 `Token.UserId` 继续表示 Key 所属用户；不创建公司级或组织级共享 Key，也不将 Key 所有者改成公司。
- 如要由公司承担费用，Key 增加明确的付款组织归属（建议概念字段 `billing_organization_id`，可为空）。用户创建 Key 时选择本人承担或当前公司承担；服务端校验其有权绑定该组织，并将此归属用于调用和结算，客户端不能在每次请求中覆盖付款组织。
- 公司管理员可按组织策略查看成员 Key 的名称、状态、创建时间、最近使用时间和付款组织等元数据，并可停用/撤销公司承担的 Key；管理员不能读取或再次展示 Key 明文。创建和查看明文的权限仍由 Key 所属用户的个人 Key 流程控制。
- 公司成员离开组织时，其公司承担的 Key 应按组织规则停用、撤销或经授权重新绑定；不得静默改成个人承担，也不得只依赖当前成员关系重写既有请求的付款归属。

### v1 不包含

- 公司自助付款、支付渠道接入、发票和供应商结算。
- 公司自定义全局模型单价；公司额度使用平台配置的定价规则扣减。
- 一名员工同时加入多个公司。
- 改写现有模型价格表达式、迁移旧倍率价格或替换任务插件合同。

## 用量看板重构方案

### 目标与入口

重构现有「数据看板」中的用量统计，避免同一页面混用全站平台统计、个人用量和公司账单口径。看板保留一个统一入口，根据平台角色和公司成员角色展示有明确数据范围的页面；页面标题下始终显示当前统计范围、筛选时间、数据更新时间和消费口径。

现有模型分析、流量和用户统计页面整体从用户导航中下线，由新看板替换；旧接口在新接口迁移完成后停用或收紧到明确的平台管理用途，不能继续被旧页面绕过新范围授权。平台运行健康、通道状态等运维指标属于平台管理视图，应与公司消费统计分开呈现。

当前实现基线：`web/src/features/dashboard/api.ts` 根据平台角色将模型统计请求发送到 `/api/data`（管理员，全站聚合）或 `/api/data/self`（普通用户，当前用户）；用户统计是平台管理员专属的 `/api/data/users`。`model/usedata.go` 将看板数据按小时写入 `quota_data`，现有聚合表没有公司归属，因此它既解释了旧页面的范围歧义，也不能直接作为新公司的隔离统计来源。此基线用于界定替换范围，不要求新方案兼容旧接口的数据语义。

### 角色与可见范围

| 身份 | 可选范围 | 展示内容与约束 |
| --- | --- | --- |
| 平台管理员 | 全部公司组织汇总；单个公司组织；选定组织下的单个用户 | 可跨组织查看汇总。查看用户时先选择组织，再从该组织成员中选择用户；不应仅凭用户名定位，以避免同名和跨组织越权。 |
| 公司管理员 | 当前公司组织汇总；当前公司组织内的单个用户 | 组织范围从已验证的成员关系取得，不能由客户端传入其他组织 ID。公司汇总包含管理员本人由公司承担的用量。 |
| 公司普通用户 | 本人 | 用户范围固定为当前登录用户，不提供组织或其他成员筛选。本人发起、但由不同主体承担的请求可以在个人视图中展示，并明确标注付款归属。 |

平台管理员的「全部公司组织」和「全平台」不是同一个范围。若平台管理员还需查看未加入公司的个人账户，应在组织汇总之外提供明确的「未归属组织」或「全平台」范围；不可把未归属用户静默混进公司汇总。公司管理员的公司总用量只统计归属于当前公司的请求。员工 Key 仍归创建它的用户所有；请求是否计入公司由请求发生时确定的组织付款归属决定。

v1 默认每个用户只加入一个公司。若后续允许一个用户同时属于多个公司，每个 Key 必须显式指定其付款组织，不能根据登录用户的当前组织任意推断费用归属。

### 筛选、指标与页面组成

- 所有角色均可选择开始/结束时间和模型名称；时间筛选以请求结算事件的 Unix 时间查询，并在页面显示实例配置时区和精确起止时间。图表时间粒度随时间跨度调整或由用户选择，并显示数据统计至哪个时间点。
- 平台管理员可按组织筛选；选择单个组织后才可筛选该组织成员。公司管理员可按当前公司成员筛选；普通成员没有成员筛选器。筛选的模型列表应包含所选期间实际出现的历史模型名，不要求模型当前仍启用。
- 页面依次展示范围与筛选区、汇总指标卡、时间趋势、模型分布、适用的组织/成员排行，以及可分页的用量明细表。平台全组织汇总可按组织展示排行；组织视图可按成员展示排行；个人视图不显示他人信息。
- 汇总指标至少明确区分已结算请求数、最终消费额度、Token 数，以及可用时的图片数量、音频/视频时长等各自单位。不同计量单位不可直接合计；额度必须标记为平台额度/配额单位，不能默认显示成真实货币金额。
- 默认统计最终结算消费：预扣不当作最终用量；失败且未收费的请求不计入消费额；退款或结算调整计入净消费额并在明细中可追溯。若产品需要查看总请求量、失败量或预估成本，应作为独立指标明确标注，不能与已结算消费混为一项。
- 同一组筛选和授权条件必须同时作用于汇总卡片、图表、明细、排行和导出；筛选状态可通过 URL 或页面状态保留，但 URL 参数不构成授权依据。导出沿用页面数据范围与字段权限，并记录导出时间和筛选范围。

### 账单与用量导出

将「账单」拆成可分析的用量明细和固定周期的消费/额度结算单，避免把 PDF 发票、额度消费报表和原始日志当作同一种文件：

- **数据看板**提供「导出报表」，导出当前角色范围和筛选条件下的汇总指标、时间趋势、模型分布，以及适用的组织/成员汇总。看板导出强调统计结果，不能只导出当前浏览器已加载的图表数据。
- **使用日志**提供「导出明细」，导出与页面相同过滤条件的逐请求消费记录，适用于核对、归档和表格分析。字段可包含请求时间、模型、请求 ID、Key 名称/掩码标识、计量事实与单位、最终额度变动、状态和付款组织；不包含 Key 明文、提示词或请求/响应正文。
- **组织管理 > 预算与用量**可提供按所选时间区间生成的「组织消费报表」入口，生成公司汇总及成员/模型分项；其权限范围仍固定为当前组织。平台管理员可在平台公司管理/用量入口选择公司或全组织范围。
- 统一使用相同的服务端查询和授权实现。平台管理员按平台选择的组织/用户范围导出；公司管理员只能导出当前公司及其成员；普通成员只能导出本人。汇总、日志、周期报表和导出下载均重复校验权限，不能因持有文件 ID 或 URL 越权。

#### 文件格式

- **XLSX 是交互式消费报表的展示格式**，在 CSV 基础数据之上生成：可在一个工作簿中提供「汇总」「按模型」「按成员」（有权限时）和「用量明细」工作表；金额/额度、时间、计量单位作为明确列，便于筛选、冻结表头和制作透视表。
- **CSV 是明细和汇总导出的基础格式**：可流式生成，文件较轻、系统间易导入。使用 UTF-8；面向 Excel 用户时可提供 UTF-8 BOM。文本列需防止以 `=`, `+`, `-`, `@` 等开头的内容被表格软件当作公式执行。
- **PDF 用于固定周期、便于阅读和留档的组织消费/额度结算单**，展示公司、周期、额度期初/发放/划拨/消费/退款调整/期末、模型与成员分项、生成时间、统计截止时间和口径说明。PDF 不适合替代可筛选的逐请求明细。
- 若平台没有真实收款、税务主体和发票流程，PDF 应称「消费报表」或「额度结算单」，不得标成税务发票或暗示是已付款的财务发票。真正的付款账单/发票需要与订单、支付状态、抬头/税务信息及发票编号等财务流程另行对接。
- v1 先交付 CSV 明细与汇总导出，XLSX 报表随后基于同一查询结果生成。PDF 周期结算单在账期、额度期初/期末与调整规则确认后作为后续能力。

#### 生成与下载流程

1. 用户从看板或使用日志点击导出，前端提交当前筛选器、格式和需要的工作表；组织、用户范围只作为筛选意图，服务端根据当前身份重新授权并构建查询条件。
2. 少量记录可同步生成；超过配置的行数或耗时阈值则创建异步导出任务，界面显示排队、生成中、可下载、失败和过期状态。
3. 导出任务保存发起者、当时授权范围、组织/用户筛选、时间区间与时区、模型筛选、格式、生成时间、统计截止时间、行数和文件过期时间，形成可审计的筛选快照。
4. 下载走需登录的受权限保护接口；下载时重新验证发起人当前权限和导出范围。文件短期保存后自动删除，不使用公开永久链接。
5. 所有汇总和明细由服务端分页/流式读取并设置行数、时间跨度和并发限制。大范围请求进入异步队列；导出内容与屏幕及其他导出使用完全相同的时间边界、结算状态和授权过滤。
6. 导出任务创建、完成、失败和下载记录审计事件；审计日志不包含文件内容、Key 明文或其他认证秘密。

行业模式参考：Stripe 将可在线查看的付款发票/收据提供为 PDF；云成本分析系统则提供 CSV（部分也提供 Parquet）作为可继续筛选和处理的数据导出。因此本方案把 PDF 限定为周期摘要单，把 XLSX/CSV 用于统计报表和用量明细。

### 数据归属、历史记录与授权

用量事件至少保存请求发生时的 `billing_organization_id`（付款组织，可为空）、`user_id`（Key 所属用户/调用账号）、`token_id`、模型名称快照、发生时间、最终结算额度、原始计量事实及单位、结算/退款状态。成员离职或组织关系变更后，历史事件仍按消费发生时的组织和用户归属查询；不能通过连接当前成员关系来重写历史账单。

当前看板使用的 `quota_data` 是按小时聚合的数据，没有组织维度，不能直接作为公司看板的数据边界。实施时应让可核对的消费记录保存不可变组织与用户归属，再构建组织/成员/模型/时间维度的查询聚合。历史记录只有在能以可信的消费时关系唯一确定组织时才能回填；无法确定的记录须标注为历史未归属，或从公司汇总开始日期中排除，并在界面说明口径，不能按当前成员关系猜测归属。

所有数据范围均由服务端执行：平台管理员可请求平台范围；公司管理员的组织 ID 取自授权后的成员关系，若请求包含用户筛选则验证该用户在该组织的历史归属；普通成员的用户 ID 固定为当前会话身份。未经授权时拒绝查询，不以隐藏前端标签或筛选控件代替后端校验。提示词、请求正文等敏感日志内容不属于看板默认字段。

## 建议的数据与服务边界

以下为方案级实体建议，具体表名和字段以实施阶段的现有模型、迁移方式和数据库兼容性审查为准：

| 实体 | 职责 |
| --- | --- |
| Organization | 公司名称、状态、创建时间、总发放额度、累计使用额度和未分配额度 |
| OrganizationMembership | 用户与公司的关系、公司角色、成员状态、创建来源；v1 对用户 ID 建立唯一约束 |
| OrganizationQuotaLedger | 公司和员工账户之间的发放、划拨、消费、退款、回收、调整记录；记录操作者、目标账户、金额、关联请求/账单 ID 和时间 |
| API Token | `UserId` 始终指向创建/拥有 Key 的用户；可选的 `billing_organization_id` 指向付款组织，不代表 Key 所有权 |
| Usage/consume log attribution | 为消费记录和任务记录固化付款组织 `billing_organization_id`（可为空）、Key 所属用户 `user_id`、`token_id` 及结算快照，支持公司、成员、模型和时间维度查询 |

余额字段可用于快速查询，账本作为可审计的变更记录。任何余额更新都要校验非负、额度上限、幂等键和公司/员工归属。需要并发保护的数据库更新使用 GORM 查询方法和项目共享的 `lockForUpdate(tx)`；SQLite 使用共享 helper 的兼容行为。预扣、结算差额和退款必须更新同一额度关系，避免用户余额与公司累计用量漂移。

平台角色与公司角色应经过独立的服务端授权检查。建议在 `service/authz/` 中定义公司级操作，例如：

- `organization.view` / `organization.update`
- `organization.members.list` / `organization.members.create` / `organization.members.update` / `organization.members.disable`
- `organization.quota.view` / `organization.quota.allocate` / `organization.quota.reclaim`
- `organization.usage.view`

公司管理员默认不能管理渠道、全站模型价格、插件、其他公司或系统配置。Root 才能执行公司创建、初始额度发放和全局管理。

公司管理员的用量视图默认展示模型、请求时间、用量、扣费和状态等业务元数据；提示词、请求/响应正文继续按现有日志隐私权限控制，不因加入公司而自动开放。

## 额度分配与消费流程

### 公司开通

1. Root 从「公司组织」菜单创建公司组织并设置初始额度，组织进入待指定管理员状态。
2. Root 创建首位公司管理员账号（见 D11）；公司身份通过成员关系授予，不新建代表公司的用户。
3. 激活公司管理员成员关系后，组织转为启用状态，并创建公司额度账本的初始发放记录。
4. 初始化后的公司未分配额度应与公司初始额度一致。

### 员工额度划拨

1. 公司管理员选择本公司成员并输入划拨额度。
2. 服务端校验操作者属于该公司且拥有额度管理权限。
3. 在原子事务中检查未分配额度、员工状态和金额边界。
4. 创建划拨账本记录，减少公司未分配余额并增加员工可用余额。
5. 额度不足、跨公司用户、负数/超限金额或重复提交均拒绝，且不能产生部分写入。

### 模型调用与结算

1. 以 API Key 解析 Key 所属用户及其固定付款组织；忽略请求正文中伪造的用户或公司 ID。
2. 复用现有预扣链路；公司承担的 Key 预扣员工划拨桶，个人 Key 预扣个人钱包，资金来源经 `FundingSource` 选择且不相互回退（见 D2、D3）；账单快照冻结用户、公司和定价版本。
3. 按现有模型表达式计算文本/多模态用量；任务插件只返回经过 schema 校验的用量事实，不直接计算额度或写余额。
4. 成功时按实际用量结算员工额度，并将实际扣费记入公司用量；预扣差额按现有 BillingSession 规则补扣或退回。
5. 失败、超时、任务轮询失败和上游取消沿用现有退款策略，并确保公司账本与员工余额同步。
6. 使用请求 ID/任务 ID 建立幂等结算键；重复回调、重复结算和退款不能重复扣减或退款。

## 复杂模型计费接入

- 文本计费继续使用 `pkg/billingexpr/`，保留输入、输出、缓存读取/写入、上下文档位、请求条件等现有能力。
- 任务计费继续使用 `usageSchema` / `usageProfiles` 和 `u("field")`。秒、数量、Token、供应商 credit 使用宿主认可的单位；分辨率/质量/模式使用枚举或布尔字段。
- 插件提交用量估算预扣；终态成功时用上游实际结算量覆盖或补充估算。失败与超时遵循任务退款合同。
- 视频/任务计费按**实际执行的插件和上游接口**选择计量事实及表达式；不得只根据公开模型名猜测一个所有渠道共用的计价单位。
- 同一模型由多个插件/渠道支持时，按执行插件选择对应的 usage schema 和计费表达式。插件缺少表达式所引用的字段时必须拒绝为未配置价格，不能静默按 0 收费。
- 客户侧扣额度、上游成本估算和毛利报表是不同指标。日志至少区分实际扣减额度与上游成本估算来源，避免把估算成本显示成可核对的供应商账单。

### 视频及异步任务的计价维度

> 决策 D7：本节的计价修正拆分为独立子计划 P6，不与组织功能共用验收。

| 接入/模型 | 计价事实候选 | 结算要求与当前实现检查 |
| --- | --- | --- |
| Volcengine Ark / Seedance | 上游实际 `completion_tokens` 或其他官方 billable usage；任务结果可同时带 `duration`、`resolution`、`frames`、`framespersecond`、`generate_audio` 等字段 | 官方 Ark SDK 的任务查询响应结构包含 `usage`、实际时长、分辨率和生成音频状态等字段。当前 Doubao 插件已按 Token、分辨率及部分视频/音频条件声明用量，并从完成响应更新 Token 和分辨率；尚需提取实际时长及其他确实参与计费的完成字段。每个端点先核对其正式账单规则，不能假设所有返回字段都收费，也不能把视频时长直接替换上游明确报告的计费 Token。 |
| 其他 Seedance 提供方 | `seconds`、`resolution`，必要时再加 `audio`、输入媒体类型等 | 同名 Seedance 模型经不同插件或提供方接入时可采用不同单位价格和公式。例如某接入按实际秒数乘分辨率单价，Ark 接入按 Token 或其官方账单字段结算。价格表达式按 `<pluginKey>::<model>` 覆盖，不能用一个全局表达式把不同渠道混为一类。 |
| Sora | 实际 `seconds`、输出 `size`/规格；未来出现质量档位时用枚举事实 | 当前插件已用请求参数预扣，并从完成响应提取实际时长和规格供结算。表达式按时长计费，并对不同尺寸/质量选档；实际费率以对应 API 版本和提供方配置为准。 |
| Alibaba Wan | 实际输出秒数、分辨率；适用时加入音频开关或输入视频时长 | 当前插件已声明秒数/分辨率，支持的 Wan3 任务可按上游输入视频时长加输出时长结算，并读取上游分辨率/音频事实。其他型号缺少完成用量时保留安全预扣，不从不完整字段猜测实际值。 |
| Kling | 供应商 `final_unit_deduction`，宿主单位 `credit` | 当前插件预扣阶段按模型、模式和请求时长估算资源单位，完成时用上游实际资源扣除量结算。应按 credit 单价计费，不把 Kling 单位冒充秒数或 Token。 |

上述事实在插件 schema 中只表示**数量或条件**，价格由表达式配置。例如，按秒的 Seedance/Sora/Wan 费率使用 `u("seconds")`，分辨率和音频条件选择不同价格分支；Kling 使用 `u("units")`；Ark 的 Token 计费使用其实际 Token 事实。表达式中的费率、插件的提交预估、完成响应里的实际用量必须分别记录和验证。

现有插件核对的代码位置为 `plugins/tasks/doubao/plugin.js`、`plugins/tasks/sora/plugin.js`、`plugins/tasks/alibaba/plugin.js`、`plugins/tasks/kling/plugin.js`。外部字段以供应商对应 API 版本为准，不应把模型能力说明等同于计费说明。

## 验收条件

### 租户与权限

- Root 可以创建、停用和恢复公司，设置初始额度和公司管理员。
- Root 创建组织时直接创建首位公司管理员账号并设置初始密码，组织创建即为 `active`。公司管理员身份保存在成员关系中，不创建公司代表用户，也不改变用户的平台角色。
- 组织创建后即可正常使用；任何停用或删除最后一位有效组织管理员的操作均被拒绝。成员账号首次登录必须修改初始密码，组织管理员重置密码后同样适用。
- 公司管理员能看到常规导航中的「组织管理」，并仅能管理当前组织成员、公司承担的 Key、预算与用量；普通成员看不到该管理入口。
- 公司管理员只能列出和管理本公司成员、额度、API Key 和用量；尝试通过改写路径参数、请求体、查询参数或 API Key 访问其他公司资源均返回拒绝。
- 员工只能查看自己的账户、API Key、余额和使用记录。
- API Key 所有者始终是具体用户；公司付款通过 Key 上固定的付款组织归属和请求结算快照表示。公司管理员管理 Key 时仅查看允许的元数据，不可读取 Key 明文；成员离开组织不能导致 Key 静默切换付款主体。
- 同一用户 Key 可选本人承担或由其有权使用的组织承担；创建和更新绑定时服务端验证组织成员关系与角色，且请求不能临时覆盖付款组织。
- 现有 Root/Admin 平台级行为保持原有权限范围；公司管理员不会被映射成平台 Admin。
- 老用户默认仍为非公司账户；迁移不能将其历史余额或历史日志静默归入任意公司。

### 用量看板

- 平台管理员可切换全部公司组织汇总、单个公司组织汇总和该组织单个用户；查看用户时必须先限定组织。未归属组织的个人用户数据单独标识，不混入公司总量。
- 公司管理员只能看到当前组织汇总及该组织成员用量；普通成员只能看到本人用量。公司汇总包括公司管理员本人由公司承担的请求。
- 页面明确显示统计对象、时间范围/时区、更新时间、消费口径及额度单位；时间和模型筛选在所有角色可用，成员筛选仅在有权的组织范围内可用。
- 汇总卡片、图表、明细、排行和导出的请求数、最终额度、Token 与多模态原始单位使用同一范围和口径；不同原始单位不合并，退款/调整能与净消费对账。
- 直接修改组织 ID、用户 ID、路径、筛选参数或导出请求不能扩大数据范围。成员离开组织后，组织历史报表仍能按消费时快照显示其历史用量。
- 新看板上线后，旧模型分析、流量、用户统计入口对所有普通用户和公司管理员下线；平台运维健康/通道指标保留在独立平台管理区域。旧接口迁移后停用或仅允许有明确平台权限的用途。
- 看板可导出当前筛选范围的汇总报表；使用日志可导出与当前过滤器相同范围的逐请求明细；组织报表只统计所选时间区间内当前公司承担的额度变化和用量。
- 小型导出可同步完成，大型导出具备异步状态、短期安全下载和过期处理；导出结果可追溯到发起人、授权范围、筛选条件、生成时间和统计截止时间。
- XLSX/CSV 的额度单位、时间和计量单位清楚；不同模型的原始单位不混加。PDF 若启用则标为消费报表/额度结算单，不能冒充税务发票。

### 额度与账本

- 公司初始发放、员工划拨、未消费额度回收、消费、预扣差额、失败退款、人工调整全部可追溯到操作者和关联请求。
- 划拨额度只转移公司未分配额度，不改变公司可用总额；消费减少员工余额并增加公司已用额度。
- 并发划拨和并发请求不能超发或透支；余额不为负，重试和重复回调不能重复结算。
- 公司可按员工查看当前余额、累计消耗、调用次数、Token/任务用量和时间范围明细；公司汇总与员工明细可以对账。
- 无公司归属的现有用户继续走现有个人账户配额流程。

### 计费与日志

- 新公司用户沿用同一套模型表达式和任务计费配置，不因加入公司改变费率，除非未来单独设计公司价格计划。
- 成功请求按实际结算用量扣减，失败请求按现有退款规则处理；Seedance 成功/失败/超时及缺失 usage 的情况都有确定行为。
- Ark Token 计价、Seedance 按秒计价、Sora 秒数/规格计价、Wan 秒数/分辨率计价和 Kling credit 计价分别以对应插件的事实及表达式准确结算，不因模型名称相似而串用计费单位。
- 消费日志和任务记录保存请求时冻结的付款公司、Key 所属员工、Key、模型、渠道和计费结果，成员之后离职或转移不能改变历史归属。

### 数据与安全

- Schema 和迁移在 SQLite、MySQL、PostgreSQL 上均通过；验证新库、从最近发布版本升级、重复启动迁移的幂等性，并检查历史余额和索引/约束保留。
- 所有租户范围检查在后端执行。公司 ID、角色、配额、费用和操作者身份不得从客户端字段直接信任。
- 成员账号创建、初始密码设置、首次登录改密码、组织管理员重置密码触及注册、登录、会话和凭据流程，实施时必须先完成适用的 OWASP Authentication / Session Management 控制审查和回归验证。

## 已确定的设计决策

以下为推荐方向，已确认。设计原则是扩展性优先：资金来源、付款方、作用范围各自可替换，v1 只实现当前需要的一种。

### D1 余额模型：划拨桶独立于个人钱包

- 决策：员工在某公司下的划拨余额是独立的余额记录，由账本驱动；个人钱包 `User.Quota` 不作为公司余额复用。
- 理由：回收只作用于划拨桶，个人充值、兑换码、签到奖励不会被误收；月度预算、每人上限等模式可作为划拨桶的重置规则扩展。
- 落点：在 `service/funding_source.go` 的 `FundingSource` 接口下新增组织划拨实现。

### D2 公司承担的 Key 扣员工划拨桶

- 决策：公司承担的 Key 的预扣和结算都作用于该员工的划拨桶；公司未分配池只是划拨来源，不直接参与预扣。
- 理由：保留每员工粒度的账本与回收能力。若以后需要“公司池直扣”，作为新的资金来源实现加入。

### D3 资金来源不回退

- 决策：公司承担的 Key 只使用划拨桶，划拨不足时直接拒绝，不回退到个人钱包或订阅。个人 Key 保持现有 `wallet_first` 等计费偏好。
- 理由：付款方在创建 Key 时确定，计费时不静默切换为个人资金，便于审计。资金来源链设计为可配置的有序列表，之后若允许订阅参与，改配置或加实现即可。

### D4 成员变更：个人余额不随成员关系移动

- 决策：加入公司不转移个人余额。成员离开或被移除时，未消费的划拨在同一事务内回收至公司未分配池并记账；其公司承担的 Key 同步停用。
- 理由：成员关系变化只产生账本事件，历史数据不被改写。若以后需要“划拨余额转入个人钱包”，作为显式账本操作新增。

### D5 账期：v1 不存储账期实体

- 决策：v1 不建账期实体。报表按所选时间区间查询，账期作为查询窗口，后续按需增加。
- 理由：账本已按时间戳记录事件，账期可以之后添加而不锁定模型。v1 不交付“组织账期报表”。

### D6 导出存储：定义存储接口，v1 使用本地磁盘实现

- 决策：导出任务状态存数据库；文件通过存储接口读写，v1 提供本地磁盘实现；下载经鉴权接口流式输出，不使用公开链接。
- 理由：本地磁盘实现简单，但仅适用于单实例部署。多实例部署需接入共享存储，以新增接口实现完成。实施前确认项目是否已有对象存储依赖。
- 格式顺序：CSV 可流式生成，作为基础格式先行；XLSX 作为其上的展示层。

### D7 视频计价修正拆分为独立计划

- 决策：Ark、Seedance、Sora、Wan、Kling 的计价修正拆分为独立子计划 P6，不与组织功能合并验收。
- 理由：该修正会改变客户实际扣费，需要单独验收和插件文档核对。现有 `<pluginKey>::<model>` 表达式覆盖机制保持不变。

### D8 公司初始额度：平台发放

- 决策：公司初始总额度由 Root 发放，在账本中记录一笔平台发放（操作者、原因、时间），计入公司未分配池。不从 Root 个人钱包划转，也不允许无来源写入额度。之后的补发、充值按同一方式扩展。
- 理由：保持总发放额度守恒，每一份公司额度都能追溯到平台发放记录。

### D9 划拨额度不过期

- 决策：员工划拨余额持续有效，与个人钱包一致，v1 不设过期。需要过期时，在划拨桶上增加过期字段，不改变账本事件模型。
- 理由：与 D1、D5 一致，v1 不引入按批次先进先出的账本。月度清零属于独立的预算模式，另行设计。

### D10 已结算消费的退款：退回原员工划拨

- 决策：人工冲正的已结算消费退回到产生该消费的员工划拨桶，并关联原请求。员工已离开公司时退回公司未分配池。退款金额不得超过该请求的已结算金额，并保证幂等。失败请求和预扣差额的自动退回，始终退回原资金来源。
- 理由：退款留在原员工的额度中，账本可以按请求对账，与 D4 的回收规则一致。

### D11 组织创建与首位管理员：Root 直接创建账号

- 决策：Root 在创建组织时直接创建首位组织管理员账号并设置初始密码，组织创建即为 `active`。不使用邀请 token、待接受邀请或 `pending_admin` 状态。
- 理由：去掉邀请流程减少认证相关的攻击面，也简化组织状态机。

### D12 成员账号：组织管理员创建，首次登录改密码

- 决策：组织管理员在本组织内直接创建成员账号并设置初始密码。账号首次登录必须先修改密码，才能使用其他功能。账号只属于本组织，创建后即为启用状态。
- 不提供“移出成员”操作，由停用（停止登录与使用，保留账号和历史用量归属）和删除（删除账号及其成员关系）代替。
- 组织至少保留一位有效管理员：不能停用或删除最后一位有效管理员。

### D13 密码重置：组织管理员重置本组织成员密码

- 决策：组织管理员可以为本组织成员设置新的初始密码，重置后该成员下次登录必须修改密码。只能操作本组织成员，每次重置写入审计日志，不记录密码本身。
- 理由：组织内部自主维护成员账号，平台 Root 不参与日常的成员密码管理。

### 子计划拆分

- P1 组织租户与授权（后端）；P1b 组织管理界面；P2 额度账本；P3 Key 付款组织与计费快照；P4 用量看板重构；P5 导出；P6 视频计价修正。
- 依赖关系：P1 → P2 → P3 → P4 → P5；P6 独立，可并行。

## 实施计划

1. **冻结产品语义**：D1–D10 已记录在「已确定的设计决策」中，实施前不存在待定的产品决策。
2. **租户领域模型与授权**：增加公司、成员关系、首次登录改密码标记和公司范围的服务端授权；保留现有平台角色和 `User.Group` 语义。
3. **额度账本与原子更新**：实现发放、划拨、回收、消费、结算差额和退款；梳理 Redis 缓存、批量更新、数据库事务和锁的边界，保持跨数据库一致性。
4. **管理 API 与看板查询**：实现 Root 公司管理、公司成员管理、员工额度管理和用量看板接口；平台、公司管理员、普通成员三种身份分别应用上述数据范围，汇总、图表、明细和导出共用服务端授权及筛选逻辑。
5. **管理界面**：组织管理页面（平台公司组织页、公司侧成员管理）由 P1b 承接；公司侧额度管理页面随 P2 实施；重构数据看板为按角色确定范围的用量页面，展示当前范围、筛选条件和更新时间。保留平台运维指标的独立入口，复用项目现有管理、图表和额度组件。
6. **Key 与账单归属**：保持 Key 所有者为用户，增加受授权的付款组织绑定；让同步请求、流式请求、图片/音频、任务插件及后台任务在预扣快照、消费日志和结算中携带不可变的付款组织、Key 所属用户和 Key 归属。
7. **Seedance 用量完善**：核对火山引擎对应 API 的返回字段和收费条件，更新插件 usage schema、实际用量提取和计费示例；按项目插件规范补充描述、单位及本地化。
8. **导出任务与文件管理**：先实现按当前看板/日志过滤器导出 CSV，再实现 XLSX；文件经存储接口读写（v1 本地磁盘实现），加入大数据量异步生成、授权下载、短期文件留存、状态查询和审计；账期 PDF 作为产品口径确认后的后续功能。
9. **迁移、验证和上线**：覆盖租户隔离、并发分配/扣减、退款、账本对账、看板筛选/导出范围和升级迁移；按发布阶段迁移已有个人账号，不推断历史公司归属，并确定公司统计历史的可信起始日期。
